### What is the mapping between token routes and grouped expert rows?

- `target_languages`: `flydsl`

#### Use when

- A route-map kernel assigns rows with per-expert atomic counters.

#### Try

- Zero the expert counters before constructing a fresh map and allocate capacity for the maximum routes received by each expert.
- Preserve route = token*topk + choice, grouped row = expert*max_m + slot, and the inverse rows_to_tokens map.

- The basic route-map builder atomically reserves an expert-local slot and emits both forward and inverse maps; a separate G2L builder handles local mapping.

### Where are route weights applied, and how are dropped routes excluded?

**Card:** `moe-weighted-gather-dropped-routes` · **type:** `semantic` · **evidence:** `source_observed` · **status:** `candidate_only` · **axes:** `combine`, `numerical_contract`, `expert_layout`

Source-observed candidate — the cited implementation exists; no performance preference is implied.

#### Machine match

- `operator_families`: `moe_dispatch_combine`, `grouped_gemm_moe`, `fused_moe_grouped_gemm`
- `target_languages`: `flydsl`, `triton`

#### Use when

- Expert outputs must be combined back into each token's output row.

#### Try

- Apply each route weight exactly once across scatter, expert epilogue and gather/reduce; record whether intermediate rows are already weighted.
- Keep a dropped route as invalid and suppress its memory load instead of clamping it to a real expert row and multiplying by zero.
- Preserve split-K accumulation and output dtype behavior when changing the combine.

#### Why this is a candidate

- The FlyDSL gather handles DROPPED_ROUTE_ROW with disabled loads, avoiding stale NaN times zero; the Triton scatter-grouped path explicitly preweights rows.

#### Keep as alternatives

- Use a separate explicit weighted sum over valid expert outputs.

### What must match at the gate/up to down-projection boundary?

**Card:** `moe-two-stage-intermediate` · **type:** `semantic` · **evidence:** `source_observed` · **status:** `candidate_only` · **axes:** `expert_compute`, `numerical_contract`, `expert_layout`

Source-observed candidate — the cited implementation exists; no performance preference is implied.

#### Machine match

- `operator_families`: `grouped_gemm_moe`, `fused_moe_grouped_gemm`
- `target_languages`: `flydsl`, `triton`

#### Use when

- MoE execution uses two expert GEMMs with an activation or gate between them.

#### Try

- Preserve gate/up ordering, the exact activation and any clipping before the down projection.
- Match the intermediate dtype, quantization scale layout and sorted-route ownership across both stages.
- Choose stage-1 split/tiling and stage-2 consumption together; a fast stage-1 output is unusable if stage 2 interprets it differently.

#### Why this is a candidate

- The FlyDSL family has distinct gate/up and down builders, including separate dequantization and scale helpers.

#### Keep as alternatives

- Keep the intermediate in a simple floating format before introducing compressed partials.
