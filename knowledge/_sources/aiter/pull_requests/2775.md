[Original source](https://github.com/ROCm/aiter/pull/2775) · SHA-256 `9a9219e3f8f652a59037b16d6b4bf4b7f02dad62c5e5f52906f244329b1a41f8`

> ## Motivation
>
> This PR adds a dedicated FlyDSL small-M HGEMM path for decode-like BF16 GEMMs where `M` is tiny while `N/K` remain large.
>
> ## Technical Details
>
> - Add a dedicated FlyDSL `small_m` HGEMM family for decode-like BF16 GEMMs with `1 &lt;= M &lt; 17`, instead of treating them as just another tuning point of generic `hgemm`.
> - Collapse M-side parallelism (`TILE_M=16`, `BLOCK_M_WARPS=1`) so wave budget is spent on the heavier N/K directions rather than the tiny M dimension.
> - Change warp mapping to an N-centric layout (`warp_m_idx=0`, `warp_n_idx=wid * WARP_N`), so one block works on one small-M slice with more N-side workers.
> - Add `N_TILE_REPEAT` to reuse loaded A fragments across multiple N tiles in the non-`B_TO_LDS` path, improving arithmetic intensity for small-M / wide-N shapes.
> - Add `PERSISTENT_N_TILES` plus dedicated `B_TO_LDS_UNROLL` / `waves_per_eu` tuning knobs for the `B_TO_LDS` path, so wide-N scheduling and load/compute overlap are tuned specifically for this regime.

For example, in gptoss_bf16_tuned_gemm.csv, the M=8, N=2880, K=4096 small-M kernel has no _WPE suffix in the kernel name, which corresponds to waves_per_eu=0, and this path also passes runtime validation.
>
> So the safer fix is not to remove 0 globally, but to:
>
> keep SMALL_M_B_TO_LDS_WAVES_PER_EU_OPTIONS = (0, 2, 4)
> canonicalize / deduplicate only the wide-N B_TO_LDS cases that collapse to the same effective compiled kernel
