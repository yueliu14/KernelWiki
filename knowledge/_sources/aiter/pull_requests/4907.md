### mtp_contract

[Original source](https://github.com/ROCm/aiter/pull/4907) · SHA-256 `f49decc8b9f7c03755bb369efd1aae675e6654378b691b7aeb5a82106cf050f6`

Source updated: 2026-09-11T13:40:34Z; captured: 2026-11-05T02:13:48.774203+00:00.

> Gated delta rule:
>
> * New FlyDSL gated delta rule: `flydsl_gdr_decode`, plus `flydsl_gdr_mtp` (vLLM) and
>   `flydsl_gdr_mtp_sglang` (SGLang) for the verify step.
> * All three MTP contracts: vLLM&#x27;s chain, SGLang&#x27;s chain with per-token snapshots, and
>   SGLang&#x27;s EAGLE tree, which reloads each arm&#x27;s parent state.
> * Opt-in via `AITER_GDR_FLYDSL=1`; the default Triton path is unchanged.
> * Sigmoid gating, the q/k L2 norm and the recurrence are one launch, with the state
>   resident in registers for the whole token loop.
> * Per-token checkpointing, so a rejected draft token rolls the state back in place
>   rather than by re-running the step.
> * The snapshot store is non-temporal wherever nothing reads it back: every contract but
>   the tree, and the tree&#x27;s own last step. It is write-once traffic either way, and at the
>   footprints where the state pool still fits in LLC it was evicting the pool that the
>   next token reads.
> * On the tree, token 1&#x27;s parent state stays in registers at either snapshot dtype. A
>   narrower snapshot owes a rounding, but a store followed by its reload is a `truncf`
>   then an `extf`, so the round trip is exact without going to memory.
> * bf16/fp16 q/k/v with an fp32 or bf16 state pool, GQA, validated at 128x128 head dims,
>   gfx942/gfx950; anything else is refused.
> * Pool and snapshot terms sit in 64-bit descriptor bases, for the reason the conv does.
> * Tiling is derived on the host from the launch grid: decode splits the value dimension
>   until `batch_size * num_v_heads` covers the part, and the MTP ladder does the same
>   before branching on the contract and the draft length, since the three contracts want
>   different splits at the same shape. `WAVES_PER_EU` rides with the one tiling that wants
>   it. `gdr_decode_tuned.csv` and the lookup that read it are deleted here: a row was keyed
>   on the shape and the batch, and the batch is half of the grid the rule already reads.
> * The public MTP dispatch accepts `draft_window` as host-side metadata, avoiding the
>    GPU-to-CPU synchronization previously needed to infer it from `cu_seqlens`. Calls
>    without this metadata fall back to Triton.
> * The default stream is selected from the input device, explicit streams are checked
>    against it, and non-contiguous output buffers are rejected.
> * CUDA Graph capture currently skips the FlyDSL route and falls back to Triton.
> * A validated private launch path avoids repeating wrapper validation in the public dispatch.

> ### 5. Measure public-entry-point latency, including dispatch synchronization
>
> Addressed.
>
> The public dispatch now accepts `draft_window` as host-side metadata. It no longer reads `cu_seqlens` back to the CPU to determine the window.
>
> The resulting behavior is:
>
> - valid host `draft_window` in eager mode: dispatch to FlyDSL;
> - missing or unsupported metadata: fall back to Triton;
> - CUDA Graph capture: fall back to Triton.
>
> The CUDA Graph fallback is now documented.
>
> We also removed duplicated validation between the support predicate and the public FlyDSL wrapper by adding a private validated launch path, and cached the architecture check.
>
> The benchmark now measures the complete `fused_rearrange_sigmoid_gated_delta_rule()` public entry with a warmed-up per-call wall-clock median. Environment-variable changes are performed outside the timed call.
>
> On gfx950 for the requested `B=1`, `T=4`, `HV=32` case, using three runs with 101 measured calls per run:
>
> - Direct FlyDSL: **36.034 µs**
> - Public entry → FlyDSL: **49.995 µs**
> - Public entry → Triton: **53.861 µs**
> - Vendored vLLM reference: **87.211 µs**
>
> The current public FlyDSL route is therefore **3.87 µs / 7.2% faster** than the same public entry with FlyDSL disabled.
>
> The absolute values differ from the reported 35.9/69.5 µs because the benchmark harness and software environment are not identical. However, the synchronization gap is consistent:
>
> - Reported regression: `69.5 - 35.9 = 33.6 µs`
> - Previous synchronized dispatch in our environment: `86.24 - 53.53 = 32.71 µs`
> - Current metadata dispatch: `49.995 - 53.861 = -3.87 µs`
>
> Thus, the previous synchronization regression is reproduced by the gap and is removed by the metadata-based dispatch.
>
> The direct and public FlyDSL results are reported separately because their input layouts differ. The direct benchmark uses separate contiguous Q/K/V tensors. The production public entry receives packed 2-D QKV; Triton consumes it directly, while FlyDSL currently constructs 4-D strided Q/K/V views. Consequently, the direct result is a kernel baseline, while the public-entry result represents the production dispatch benefit.
