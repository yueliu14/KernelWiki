> ## Motivation
>
> The second MoE GEMM and its following collective form a critical serving path
> for DeepSeek-V4. Executing GEMM2, all-reduce/reduce-scatter, and the
> shared-expert add independently leaves avoidable launch, memory-traffic, and
> synchronization overhead, while production DPA introduces ragged per-rank token
> counts that fixed-layout kernels cannot represent efficiently.
>
> This PR turns the comm-fused MoE Stage2 path into a production-ready Aiter
> runtime. It provides tuned Mega, Direct, and Window collective families across
> the serving token range; supports compact ragged reduce-scatter; unifies tuning
> and runtime configuration; makes synchronization and backend capabilities
> explicit; and preserves the existing Stage2 callback ABI for downstream users.
>
> For the production DeepSeek-V4 shape, a clean-cache, skew-routing TP8 re-run
> shows **19.88%–77.47%** speedup for low-token Mega all-reduce,
> **41.79%–119.66%** for Window all-reduce, and **24.10%–86.77%** for Window
> reduce-scatter. Direct reduce-scatter measured through the production-equivalent
> external-reuse synchronization path improves M128, M512, and M1024 by
> **1.33%**, **2.11%**, and **6.30%**, respectively. Downstream DPA serving
> improves throughput by **6.39%–10.18%** across concurrency 64–1024 with GSM8K
> accuracy preserved.
>
> ## Technical Details
>
> ### Tuned Stage2 collective families
>
> - Integrate and tune three complementary kernel families:
>   - **Mega** for low-token all-reduce buckets.
>   - **Direct** for latency-sensitive BF16 reduce-scatter plus shared-expert add.
>   - **Window** for larger all-reduce and reduce-scatter workloads.
> - Improve Window producer scheduling, collective ordering, cache policy, local
>   worker assignment, and drain behavior.
> - Support dynamic route scaling and native compact MXFP4 communication payloads
>   for validated configurations.
> - Keep eager and CUDA graph execution on the same runtime selection path with
>   graph-safe workspace ownership and lifetimes.
>
> ### Unified configuration and runtime selection
>
> - Make the standard model tuned FMoE CSV the single source of truth for both
>   ordinary and comm-fused winners.
> - Extend `ShapeKey` and the tuner schema with collective type, shared-add, and
>   backend configuration metadata.
> - Align tuner output with production lookup so a tuned row can be consumed
>   directly by the runtime.
> - Expose the shared `bucket_for()` helper and explicit runtime capabilities such
>   as `supports_ragged_m` and `supports_external_reuse_sync`.
> - Remove superseded standalone comm-fused winner/untuned CSVs, legacy JIT config
>   alias plumbing, and obsolete atomic/output-shard experiments.
>
> ### Compact ragged reduce-scatter
>
> - Accept `reduce_scatter_sizes` and compute each rank&#x27;s real `local_rows` and
>   `rank_offset`.
> - Select the kernel bucket from the maximum loaded rank while keeping the actual
>   input compact.
> - Return only the calling rank&#x27;s real rows instead of a padded shard.
> - Advertise layout support through an explicit capability contract so callers
>   can select compact or fixed-layout collection without implementation-specific
>   probing.
>
> ### Synchronization and callback compatibility
>
> - Add explicit external reuse synchronization for Direct kernels. An enclosing
>   DPA input gather can prove that every peer consumed the previous partial
>   buffer, allowing the production path to skip a redundant standalone wait.
> - Retain the internal fallback synchronization for callers that cannot provide
>   that proof.
> - Separate producer/consumer synchronization for the Stage2 input and
>   shared-expert add, and simplify the Direct reduction/add path.
> - Preserve the legacy zero-argument `before_stage2()` callback and add the
>   explicit row-aware `before_stage2_for_rows(rows)` callback. Supplying both is
>   rejected to keep behavior unambiguous.
>
