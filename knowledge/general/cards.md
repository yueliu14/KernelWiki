# General methods — decision cards

Generated by `tools/agent/build_cards.py` from `corpus/decisions.yaml` (maintained on `main`); edit the YAML, not this file.

How to read a card:
- **Evidence** — `reported`: an upstream PR or benchmark reported an outcome (not reproduced here; the outcome
  line says what was reported). `source-only`: observed in shipped source or configs; it shows what an
  implementation does, not that it wins. Treat both as hypotheses and measure on your own kernel and shapes.
- **Applies** — the languages/dtypes/GPUs the card was derived from. For a kernel in another language the card is a
  porting idea, not a recipe.
- `constraint` cards are correctness or validity rules: check them before trusting a speedup.

<a id="method-causal-resource-model"></a>
### How should roofline and counter observations guide a concrete experiment?

`method-causal-resource-model` · performance · evidence: **reported** · applies: lang all

**When:** The deployed CU count, dtype, shape and execution boundaries are known.
**Try:**
- Count required bytes and FLOPs for the actual semantics, including sparse gathers, partial buffers and scale metadata; use the resources actually available to the process.
- Attribute instructions and dependencies to the hot region, and compare plausible traffic/compute bounds to a matching measurement.
- Use a controlled ablation to test the proposed cause. A deliberately incomplete control must stay separate from correctness-gated candidate results.
**Why:** Historical reports found inflated peak denominators, removable scratch traffic and misleading instruction/counter proxies behind apparently exhausted kernels.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** A high counter or fraction of peak does not prove that reducing it will improve latency. Bounds and measured performance are separate claims.
**Reported:**
- constraint: Historical reports found inflated peak denominators, removable scratch traffic and misleading instruction/counter proxies behind apparently exhausted kernels.

<a id="method-conditional-negative-results"></a>
### When should an optimization direction that previously failed be tested again?

`method-conditional-negative-results` · performance · evidence: **reported** · applies: lang all

**When:** A negative result was obtained for a particular implementation, operating regime and baseline.
**Try:**
- Preserve the mechanism and tested conditions of a negative result, then revisit it when dtype, tile, accumulation, cache footprint, compiler or timing protocol changes.
- Test a proposed combination against the same baseline and against its strongest component; individually positive changes can interfere or become unreachable after dispatch changes.
- Keep corrected or withdrawn explanations with their scoped conclusion; a historical gain, an artifact-integrity check and an independently reproduced deployment are different evidence claims.
**Why:** Several discarded directions became useful after the limiting resource or selected implementation changed; other combinations erased an earlier gain.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** An unmeasured idea, build failure and measured no-gain result are different outcomes. None establishes a permanent prohibition.
**Reported:**
- mixed: Several discarded directions became useful after the limiting resource or selected implementation changed; other combinations erased an earlier gain.
- constraint: The imported campaign summary distinguishes measured gains from deployment reproduction and records withdrawn explanations and negative experiments; its per-model artifacts are not included in KernelWiki.

<a id="method-end-to-end-attribution"></a>
### How should isolated improvements be evaluated as an end-to-end change?

`method-end-to-end-attribution` · performance · evidence: **reported** · applies: lang all

**When:** The workload contains multiple kernels or phases, potentially with host work and communication overlap.
**Try:**
- Screen a candidate using its time share within a clearly stated boundary, then measure the full workload with the intended phase mix and topology.
- Report a combined improvement as a combined result unless independent ablations isolate component effects.
- Retain correct modest improvements only when the final combination passes the full correctness and performance gate.
- Choose the deployment phase and operating point explicitly; estimate startup, warmup and repetition costs before deciding whether the expected end-to-end gain can be resolved within the available time.
- Re-time the selected change on the serving path: isolated kernel rankings and phase-specific improvements can change under the deployment workload.
**Why:** Historical serving summaries found that individually small kernels and phase-specific gains did not translate proportionally to whole-model throughput.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Do not multiply a time share by a phase fraction a second time if the measured share already includes that phase weighting. An Amdahl estimate is a model, not a measured serving gain.
**Reported:**
- mixed: Historical serving summaries found that individually small kernels and phase-specific gains did not translate proportionally to whole-model throughput.
- constraint: Reported campaigns found isolated kernel wins with negligible serving impact, ranking reversals after deployment, and experiment costs large enough to determine which gains were measurable.

<a id="method-grid-and-lifetime-contract"></a>
### When can a new grid axis improve a composed kernel chain?

`method-grid-and-lifetime-contract` · performance · evidence: **reported** · applies: lang all

**When:** A stage partitions only tokens while another independent dimension can supply useful parallelism.
**Try:**
- Check useful workgroups against available CUs, then partition the independent dimension while preserving output ownership and producer/consumer lifetimes.
- Hoist invariant bounds checks only when the full dynamic domain is covered; inspect the generated code and validate tails.
- Measure each stage and the complete chain after combining grid, tile and fusion changes.
**Why:** A historical composed TileLang chain benefited from exposing hidden-dimension parallelism and removing invariant loop work; further fusion did not automatically improve the result.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** The original combined speedup cannot be assigned independently to each technique. More workgroups may increase memory traffic or change the limiting resource.
**Reported:**
- mixed: A historical composed TileLang chain benefited from exposing hidden-dimension parallelism and removing invariant loop work; further fusion did not automatically improve the result.

<a id="method-host-and-replay-floor"></a>
### Is launch or host work inside the metric being optimized?

`method-host-and-replay-floor` · performance · evidence: **reported** · applies: lang all

**When:** A small kernel may be dominated by allocation, argument binding, dispatch or graph replay rather than its device body.
**Try:**
- Measure eager and captured execution using the actual benchmark bracket; compare a minimal launch/replay control on the same stack.
- Use controlled host-delay or allocation probes to determine whether that work is exposed or hidden by queued GPU work.
- Recheck state lifetime and allocator behavior before attributing periodic per-case differences to device code.
**Why:** Some reports benefited from reducing host work while others timed only captured device execution or paid more for graph replay than for a direct launch.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Device time and host time from different profiling protocols cannot simply be subtracted to claim exact overhead. Empty controls bound possibilities; they are not deployable implementations.
**Reported:**
- mixed: Some reports benefited from reducing host work while others timed only captured device execution or paid more for graph replay than for a direct launch.

<a id="method-live-binary-and-integration"></a>
### How can an optimization be tied to the code and call path that actually ran?

`method-live-binary-and-integration` · performance · evidence: **reported** · applies: lang all

**When:** Compilation caches, imported aliases or serving workers can resolve a different implementation from the edited source.
**Try:**
- Record source and binary identities privately; inspect the compiled artifact and prove the intended callable executes in every relevant worker.
- After changing module-level flags or included headers, invalidate or isolate the relevant compilation cache and verify that the changed binary was loaded.
- Validate graph capture, stream handling, dynamic inputs and repeated calls on the real integration path before measuring end-to-end behavior.
- Record the effective process environment privately and verify positive selection markers plus expected negative/fallback markers on every relevant rank.
- Restart processes and recapture graphs after configuration changes when the runtime caches the old selection; a file changed on disk does not establish deployment.
**Why:** Historical summaries repeatedly reported unchanged or stale binaries and unpatched importing call sites being mistaken for optimization results.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** A loaded-module message does not prove the timed path used the candidate. A correct isolated kernel does not establish successful serving integration.
**Reported:**
- constraint: Historical summaries repeatedly reported unchanged or stale binaries and unpatched importing call sites being mistaken for optimization results.
- constraint: Historical campaigns reported configuration changes remaining inert under process or graph caches, and partial rank engagement despite plausible benchmark output.

<a id="method-paired-measurement-controls"></a>
### How can a small performance change be distinguished from measurement drift?

`method-paired-measurement-controls` · performance · evidence: **reported** · applies: lang all

**When:** The candidate and baseline implement the same contract and are timed under the actual execution protocol.
**Try:**
- Interleave paired baseline/candidate blocks in both orders and include an A/A control. Keep warmup, allocations, clocks, power limits and contention comparable.
- Report per-case results and uncertainty with the intended workload weights. Choose a justified acceptance rule instead of inheriting a historical fixed percentage.
- Check correctness independently of the edited implementation, and separate a counter change from a latency change.
- Re-establish the noise floor on the actual host and wait for stable warmup after each restart; do not inherit a fixed number of warmup rounds from another run.
- Compare serving-accuracy changes and gate margins with the accuracy harness's repeatability; an apparent pass near the threshold may need additional validation.
**Why:** Historical experiments found order bias, power/clock drift and timing-bracket effects large enough to reverse small apparent wins.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** A non-overlap rule or median alone is not a universal statistical guarantee. Raw timing histories remain private.
**Reported:**
- constraint: Historical experiments found order bias, power/clock drift and timing-bracket effects large enough to reverse small apparent wins.
- constraint: Reported serving campaigns found host-dependent restart scatter, cold-run effects and accuracy margins that required fresh controls on the actual environment.

### What resource limits occupancy on a matrix-core kernel?

`method-register-limited-occupancy` · performance · evidence: **reported** · applies: lang all

**When:** Matrix instructions use architecture-specific vector and accumulator register allocation.
**Try:**
- Use the code object and the target architecture allocation rules to account for VGPRs, AGPRs, LDS, waves and workgroups together.
- Verify achieved residency and scratch behavior after a change; lower register counts or higher waves per SIMD are not sufficient evidence of improved throughput.
**Why:** A historical CDNA4 analysis found that counting only one register class overestimated available occupancy.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Register accounting is architecture- and toolchain-specific; no fixed register budget or waves-per-CU target applies to every device.
**Reported:**
- constraint: A historical CDNA4 analysis found that counting only one register class overestimated available occupancy.
