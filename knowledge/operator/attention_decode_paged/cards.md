### When should KV loads bypass cache or use explicit prefetch?

`decode-kv-cache-policy` · performance · evidence: **reported** · applies: lang all

**When:** The KV working set, reuse across heads/calls and load representation can be measured for each served regime.
**Try:**
- First remove avoidable scratch or repeated gathers; compare cache policy separately for each operand and workload bucket.
- Inspect generated loads to prove the intended cache modifier survives vectorization, with alignment and tail masking preserved.
- When testing global-to-LDS transfer, measure whether it buys useful prefetch depth without excessive live registers or LDS pressure.
**Why:** Historical decode reports found both positive and negative non-temporal results; footprint changes reversed the preferred policy. A DMA instruction alone did not establish a gain.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Read-once source code does not imply zero hardware/cache reuse. Re-test policies after changing KV dtype, tile geometry or concurrency.
**Reported:**
- mixed: Historical decode reports found both positive and negative non-temporal results; footprint changes reversed the preferred policy. A DMA instruction alone did not establish a gain.

### When can combining split-KV stages in one dispatch beat a separate reduction?

`decode-single-dispatch-merge` · performance · evidence: **reported** · applies: lang all

**When:** Partial results are shared across workgroups and the complete publish/signal/consume protocol can be implemented correctly.
**Try:**
- Price the second dispatch and its reduction work against the cost of cross-workgroup visibility, counter traffic, held registers and LDS residency.
- Use a memory-model-correct protocol with initialized per-invocation state, proper scope and ordering; validate concurrent streams and repeated calls.
- Compare small and wide grids separately and retain the two-dispatch path when protocol/resource costs exceed the saved launch.
**Why:** Historical summaries reported both useful fused merges and large regressions caused by synchronization or residency cost; fewer launches did not consistently mean lower latency.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Instruction-level fence shortcuts from one report are not portable synchronization recipes. A last-arriver scheme must not require unscheduled workgroups to run while resident workgroups spin.
**Reported:**
- mixed: Historical summaries reported both useful fused merges and large regressions caused by synchronization or residency cost; fewer launches did not consistently mean lower latency.

### How should a decode tile and its split grid be sized together?

`decode-tile-and-split-geometry` · performance · evidence: **reported** · applies: lang all

**When:** The kernel has head-width-dependent resource use, paged or windowed KV, and a legal split/reduce path.
**Try:**
- Inspect the real launched grid before tuning; decouple logical KV tile size from storage page size only if the gather implementation supports it.
- Sweep tile size, useful split count, warp count and pipeline depth together, accounting for head width, CU count and scratch round trips.
- Pass identical tile/segment bounds through producer and reducer, cull truly empty window segments and validate widest heads and ragged tails.
**Why:** Historical reports improved underfilled or oversplit launches through coupled geometry changes; their optimal workgroups-per-CU targets differed, and a previously helpful memory change could regress after retiling.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Neither one workgroup per CU nor a fixed multiple is a universal optimum. Graph metadata and fallback branches must remain valid for every supported shape.
**Reported:**
- mixed: Historical reports improved underfilled or oversplit launches through coupled geometry changes; their optimal workgroups-per-CU targets differed, and a previously helpful memory change could regress after retiling.

### How do page layout and compiled template contracts constrain paged-attention tuning?

`paged-attention-live-layout-dispatch` · performance · evidence: **reported** · applies: lang all

**When:** The served path uses paged or ragged KV with a version-specific dispatch/template selector.
**Try:**
- Inspect the actual page size, cache dtype, head width and called entry before selecting a rewrite or library candidate.
- Keep producer and reduce partition sizes consistent with the compiled kernel; validate a partition sweep before accepting its latency.
- Check shape/dtype eligibility and actual engagement of experimental template variants, including graph execution.
**Why:** Historical reports found that non-power-of-two and one-token pages changed the usable path; an experimental BF16/head-width-specific template existed despite an earlier no-knob claim. Incompatible partition sizes produced invalid fast results.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Do not generalize old framework flags or template eligibility to another revision. A template intended for BF16 KV may cease to apply after KV quantization.

<a id="attention-paged-kv-addressing"></a>
### What must remain consistent when loading a paged KV cache?

`attention-paged-kv-addressing` · constraint · evidence: **source-only** · applies: lang triton/flydsl/gluon; requires `paged_kv`

**When:** KV positions are logical sequence positions mapped through a per-request page table.
**Try:**
- Resolve each logical token through its block-table entry and its offset within the page; preserve the independent K/V cache strides.
- Distinguish a compute tile from a cache page: the general path may need multiple page-table lookups, while TILE_SIZE == BLOCK_SIZE enables a specialized path.
- Validate ragged sequence lengths, nontrivial block-table strides and the final partial page against the actual cache producer.
**Why:** The unified Triton kernel has distinct TILE_SIZE == BLOCK_SIZE and general page-lookup paths, with explicit K and V strides.
**Alternatives:** Use the general paged load path before specializing page-aligned tiles.
**Limits:**
- A page-size constant is not evidence that all cache layouts use the same physical order.
- Source availability does not establish support for every dtype or head dimension.
