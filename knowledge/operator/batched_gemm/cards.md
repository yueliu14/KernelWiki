- **Evidence** — `reported`: an upstream PR or benchmark reported an outcome (not reproduced here; the outcome

- **Applies** — the languages/dtypes/GPUs the card was derived from. For a kernel in another language the card is a
  porting idea, not a recipe.

### Which batch and scale layouts does the MXFP8 BMM wrapper accept?

`batched-mxfp8-scale-layout` · constraint · evidence: **source-only** · applies: lang flydsl

**When:** The selected implementation matches the cited path and its input contract.
**Try:**
- Preserve XQ [M,B,K], preshuffled WQ [B,N,K] and Out [M,B,N]; batch is not a freely broadcast dimension in this entry point.
- Select a runner using the architecture, weight-scale block and activation-scale orientation together.
- On the gfx950 path distinguish 32x32 from 128x128 weight-scale blocks and row-major from the supported column-major activation scales.
**Why:** The cited source declares these operations and checks; the combination is part of its interface.
**Alternatives:** Keep a simpler implementation with the identical numerical and layout contract for comparison.
**Limits:** This is an implementation precedent, not a measured performance preference on a new workload.

- gain reported: The shared MXFP8 implementation has reported tuned linear-GEMM gains; the PR gives no separate wo_a BMM speedup or ablation of this contract/heuristic.
