### When can one program share gathered KV across more query heads?

`gqa-head-tile-gather-reuse` · performance · evidence: **reported** · applies: lang all

**When:** Grouped heads attend to compatible gathered KV, and output ownership remains separate for every query/head.
**Try:**
- Widen the head tile to reduce repeated KV gathers, measuring accumulator pressure and occupancy together.
- Inspect QK and PV warp layouts and remove only provably redundant rendezvous or indexing work.
- Preserve online-softmax maxima/denominators, per-query masks and ragged-tail handling; validate the supported logit domain.
**Why:** Historical sparse/GQA reports benefited from head-group tiling, but instruction-count reductions and occupancy changes did not translate uniformly to latency.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Do not freeze a softmax maximum, drop normalization updates or clamp logits merely because sampled cases pass. Such changes require an explicit semantic bound or accepted approximation contract.
**Reported:**
- mixed: Historical sparse/GQA reports benefited from head-group tiling, but instruction-count reductions and occupancy changes did not translate uniformly to latency.

### Can KV storage be narrowed while retaining the attention compute contract?

`gqa-storage-precision-contract` · performance · evidence: **reported** · applies: lang all

**When:** KV traffic is limiting and the accepted accuracy contract permits a storage-precision experiment.
**Try:**
- Separate storage, conversion and dot/accumulation dtypes; derive packed K addressing from element size and validate scale/layout compatibility.
- Gate QK, softmax probabilities and PV precision changes independently, including near-cancellation outputs and model accuracy.
- Re-measure cache residency and occupancy after the byte footprint changes.
**Why:** Some historical attention cases benefited from FP8 KV storage with wider in-register computation, while narrowing a different dot or intermediate failed its accuracy gate.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** A successful KV-storage change does not validate quantizing softmax probabilities or QK arithmetic. Quantizer distributions and extreme inputs matter.
**Reported:**
- mixed: Some historical attention cases benefited from FP8 KV storage with wider in-register computation, while narrowing a different dot or intermediate failed its accuracy gate.
**Read more:** [README.md](README.md), [README.md](../../general/README.md)

### How should query heads share KV heads without changing GQA/MQA semantics?

`attention-gqa-head-mapping` · semantics · evidence: **source-only** · applies: lang triton/gluon/flydsl

**When:** The workload has more query heads than KV heads.
**Try:**
- Preserve the query-head-to-KV-head mapping and the required divisibility when grouping query heads into a workgroup.
- Treat query-head grouping as a reuse opportunity; tune the group and tile sizes while retaining each query head's separate normalization state.
- Check unequal query/KV head counts and nontrivial strides, not only ordinary equal-head MHA.
**Why:** The unified kernel separates query head indexing from KV-head indexing while carrying per-query softmax state.
**Alternatives:** One independent query head per program is a simple baseline for the same shared KV cache.
**Limits:** MQA/GQA reuse does not imply the same best workgroup geometry for every head ratio.
