### Which host and synchronization invariants accompany device-side MoE communication?

`moe-communication-arena-lifetime` · constraint · evidence: **source-only** · applies: lang flydsl

**When:** The candidate reuses the tensor-parallel MegaMoE device communication design.
**Try:**
- Reserve symmetric arena regions in the same order across ranks and keep the mappings alive for all in-flight kernels.
- Preserve readiness/epoch and buffer-reuse dependencies along with peer addressing; copying the compute loop alone is insufficient.
- Separate TP reductions from EP token routing when defining ownership and output semantics.
**Why:** The arena implementation maps peer allocations, and the communication helpers poll readiness and use rank-indexed metadata.
**Alternatives:** Use explicit library collectives between compute stages before attempting device-side overlap.
**Limits:**
- This is a TP communication precedent, not evidence that an arbitrary EP topology is supported.
- No multi-GPU performance or deadlock-free execution was measured for this corpus.

<a id="moe-route-map-capacity"></a>
### What is the mapping between token routes and grouped expert rows?

`moe-route-map-capacity` · constraint · evidence: **source-only** · applies: lang flydsl

**When:** A route-map kernel assigns rows with per-expert atomic counters.
**Try:**
- Zero the expert counters before constructing a fresh map and allocate capacity for the maximum routes received by each expert.
- Preserve route = token*topk + choice, grouped row = expert*max_m + slot, and the inverse rows_to_tokens map.
- For distributed or masked experts, use the explicit global-to-local map variant and retain the dropped-route convention through the consumer.
**Why:** The basic route-map builder atomically reserves an expert-local slot and emits both forward and inverse maps; a separate G2L builder handles local mapping.
**Alternatives:** Use the sorted-token representation with a compatible downstream GEMM.
**Limits:**
- The atomic reservation is not a capacity check: overload must be prevented or handled by the caller.
- Atomic slot order need not match original token order.
**Reported:**
- no result: PR #3460 introduces the route-to-grouped-row and inverse maps; it does not quantify a speedup or establish all later capacity/drop behavior.

### What does fusing route mapping, MX quantization and scatter commit the consumer to?

`moe-route-quant-scatter-fusion` · performance · evidence: **source-only** · applies: lang flydsl

**When:** The candidate uses per-1x32 MX activation quantization and expert-grouped storage.
**Try:**
- Fuse route assignment, payload quantization and scale placement only when the GEMM accepts exactly that payload/scale layout.
- Retain the zero-initialized route counter, per-expert capacity and valid-row metadata.
- Keep the scale-preshuffle transform coupled to the grouped row and the consumer's WMMA/MFMA layout.
**Why:** The fused builder replaces separate route-map, quant, token-copy and scale-preshuffle passes, with explicit per-32-element scale handling.
**Alternatives:** Keep the four stages separate to isolate layout and numerical correctness before fusion.
**Limits:**
- This is a source precedent, not a measured reduction in end-to-end latency.
- A backend that expects contiguous scales cannot directly consume preshuffled scales.
**Reported:**
- no result: PR #3851 incorporates the fused route/quant/scatter path; no measured performance benefit is reported in the reviewed discussion.

### Where are route weights applied, and how are dropped routes excluded?

`moe-weighted-gather-dropped-routes` · semantics · evidence: **source-only** · applies: lang flydsl/triton

**When:** Expert outputs must be combined back into each token's output row.
**Try:**
- Apply each route weight exactly once across scatter, expert epilogue and gather/reduce; record whether intermediate rows are already weighted.
- Keep a dropped route as invalid and suppress its memory load instead of clamping it to a real expert row and multiplying by zero.
- Preserve split-K accumulation and output dtype behavior when changing the combine.
**Why:** The FlyDSL gather handles DROPPED_ROUTE_ROW with disabled loads, avoiding stale NaN times zero; the Triton scatter-grouped path explicitly preweights rows.
**Alternatives:** Use a separate explicit weighted sum over valid expert outputs.
**Limits:** A zero weight does not make an invalid or uninitialized read numerically safe.
**Reported:**
- no result: PR #3460 establishes the weighted gather part of this contract. Its unused-slot convention differs from the later pinned negative-row handling and supplies no measured gain.
**Existing implementations:** triton: _scatter_grouped multiplies rows by Gammas before a subsequent unweighted reduction.
