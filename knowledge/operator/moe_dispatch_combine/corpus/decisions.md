### What is the mapping between token routes and grouped expert rows?

**Card:** `moe-route-map-capacity` · **Type:** `constraint` · **Evidence:** `source_observed`

**Axes:** `expert_layout`, `implementation_contract`

#### Applicability

- `operator_families`: <code>moe_dispatch_combine</code>, <code>grouped_gemm_moe</code>, <code>fused_moe_grouped_gemm</code>
- `target_languages`: <code>flydsl</code>

#### Use when

- A route-map kernel assigns rows with per-expert atomic counters.

#### Try

- Zero the expert counters before constructing a fresh map and allocate capacity for the maximum routes received by each expert.
- Preserve route = token*topk + choice, grouped row = expert*max_m + slot, and the inverse rows_to_tokens map.
- For distributed or masked experts, use the explicit global-to-local map variant and retain the dropped-route convention through the consumer.

#### Rationale

- The basic route-map builder atomically reserves an expert-local slot and emits both forward and inverse maps; a separate G2L builder handles local mapping.

#### Keep as alternatives

- Use the sorted-token representation with a compatible downstream GEMM.

### What does fusing route mapping, MX quantization and scatter commit the consumer to?

**Card:** `moe-route-quant-scatter-fusion` · **Type:** `performance_candidate` · **Evidence:** `source_observed`

**Axes:** `expert_layout`, `numerical_contract`, `data_movement`

#### Applicability

- `operator_families`: <code>moe_dispatch_combine</code>, <code>fused_moe_grouped_gemm</code>
- `target_languages`: <code>flydsl</code>

#### Use when

- The candidate uses per-1x32 MX activation quantization and expert-grouped storage.

#### Try

- Fuse route assignment, payload quantization and scale placement only when the GEMM accepts exactly that payload/scale layout.
- Retain the zero-initialized route counter, per-expert capacity and valid-row metadata.
- Keep the scale-preshuffle transform coupled to the grouped row and the consumer's WMMA/MFMA layout.

#### Rationale

- The fused builder replaces separate route-map, quant, token-copy and scale-preshuffle passes, with explicit per-32-element scale handling.

#### Keep as alternatives

- Keep the four stages separate to isolate layout and numerical correctness before fusion.

### Where are route weights applied, and how are dropped routes excluded?

**Card:** `moe-weighted-gather-dropped-routes` · **Type:** `semantic` · **Evidence:** `source_observed`

**Axes:** `combine`, `numerical_contract`, `expert_layout`

#### Applicability

- `operator_families`: <code>moe_dispatch_combine</code>, <code>grouped_gemm_moe</code>, <code>fused_moe_grouped_gemm</code>
- `target_languages`: <code>flydsl</code>, <code>triton</code>

#### Use when

- Expert outputs must be combined back into each token's output row.

#### Try

- Apply each route weight exactly once across scatter, expert epilogue and gather/reduce; record whether intermediate rows are already weighted.
- Keep a dropped route as invalid and suppress its memory load instead of clamping it to a real expert row and multiplying by zero.
- Preserve split-K accumulation and output dtype behavior when changing the combine.

#### Rationale

- The FlyDSL gather handles DROPPED_ROUTE_ROW with disabled loads, avoiding stale NaN times zero; the Triton scatter-grouped path explicitly preweights rows.

#### Keep as alternatives

- Use a separate explicit weighted sum over valid expert outputs.

#### Other implementations

- **triton** — _scatter_grouped multiplies rows by Gammas before a subsequent unweighted reduction. [aiter_b3ad6c46:src_8b4846cb32c13ce3](source_evidence.md#aiter_b3ad6c46-src_8b4846cb32c13ce3), [aiter_b3ad6c46:src_330eb5ef722c9789](source_evidence.md#aiter_b3ad6c46-src_330eb5ef722c9789)

### Which host and synchronization invariants accompany device-side MoE communication?

**Card:** `moe-communication-arena-lifetime` · **Type:** `constraint` · **Evidence:** `source_observed`

**Axes:** `communication`, `implementation_contract`

#### Applicability

- `operator_families`: <code>moe_dispatch_combine</code>, <code>fused_moe_grouped_gemm</code>
- `target_languages`: <code>flydsl</code>

#### Use when

- The candidate reuses the tensor-parallel MegaMoE device communication design.

#### Try

- Reserve symmetric arena regions in the same order across ranks and keep the mappings alive for all in-flight kernels.
- Preserve readiness/epoch and buffer-reuse dependencies along with peer addressing; copying the compute loop alone is insufficient.
- Separate TP reductions from EP token routing when defining ownership and output semantics.

#### Rationale

- The arena implementation maps peer allocations, and the communication helpers poll readiness and use rank-indexed metadata.

#### Keep as alternatives

- Use explicit library collectives between compute stages before attempting device-side overlap.
