### Is router top-k limited by launch preparation or by the selection network?

`router-launch-and-selection-cost` · performance · evidence: **reported** · applies: lang all

**When:** Small router rows expose a host/launch floor while larger rows may be selection-bound.
**Try:**
- Measure both regions separately and compare direct compiled launches with graph replay using the same contract.
- Cache invariant compilation/options only with complete validity checks, stream safety and updated dynamic arguments.
- For small fixed k, compare iterative selection or partitioned merges with the existing network, preserving tie rules, indices, output masks and softmax semantics.
**Why:** Historical router reports found substantial host-path effects for small cases and narrower device benefits for larger ones; replay and blindly combined device changes could regress.
**Alternatives:** Keep the existing correct implementation as the baseline and fallback; compare changes on the same workload.
**Limits:** Pointer-only or trusted-steady-state shortcuts are not general cache keys. An oracle that imports the edited helper is not independent correctness evidence.
**Reported:**
- mixed: Historical router reports found substantial host-path effects for small cases and narrower device benefits for larger ones; replay and blindly combined device changes could regress.

### When is the specialized HERD routing path a valid candidate?

`moe-herd-routing-profile` · constraint · evidence: **source-only** · applies: lang flydsl

**When:** A candidate intends to reuse the FlyDSL HERD sigmoid routing implementation.
**Try:**
- Check the source's supported (score_func, experts, topk) profile instead of treating HERD as a generic top-k replacement.
- Preserve correction-bias scoring, candidate generation, final weight normalization and routed_scaling_factor as distinct parts of the contract.
- Honor the token-count, contiguous expert-column, output dtype/device and wave64 checks in _unsupported_reason.
**Why:** The orchestration separates sigmoid-bias candidate selection from finalize, and publishes explicit narrow supported profiles.
**Alternatives:** Use the existing general routing implementation for unmatched profiles.
**Limits:**
- The existence of a fast-path wrapper says nothing about its speed on a new workload.
- Do not substitute sigmoid routing for a softmax or grouped-routing contract.
**Reported:**
- gain reported: The Kimi-K3 report supports a conditional HERD candidate; realistic bias and the supported profile matter, and no numeric speedup is encoded.

### Which outputs of expert sorting are part of the downstream GEMM ABI?

`moe-sort-padding-sentinels` · constraint · evidence: **source-only** · applies: lang flydsl

**When:** Token/expert routes are sorted and padded into expert-aligned work blocks.
**Try:**
- Carry sorted token IDs, sorted route weights, sorted expert IDs and valid-count metadata together.
- Use the same unit_size for sorting/padding and downstream compute; preserve sentinel slots rather than interpreting padding as real routes.
- Size and initialize the sorting workspace according to token count, experts, top-k and alignment.
**Why:** The sorting wrapper passes all four output structures and unit_size together; the kernel has explicit expert-block and sentinel-fill helpers.
**Alternatives:** Keep sorting separate from GEMM while validating a new expert layout.
**Limits:**
- A padding factor selected for one GEMM tile is not automatically legal for another.
- The cached wrapper workspace is not by itself evidence of arbitrary concurrent-stream safety.
**Reported:**
- mixed: The sorting replacement has reported serving gains and mixed per-shape operator results; these do not isolate the benefit of padding or a particular ABI field.
