<a id="single-trip-full-width-qk-pv-dots"></a>
### On an attention path that processes all selected KV slots in one tile, should QK and PV be computed as one full head-width dot instead of several head-dim-group dots?

**Card:** `single-trip-full-width-qk-pv-dots` · **Type:** `performance_candidate` · **Evidence:** `reported_experience`

**Axes:** `compute_schedule`, `data_movement`

#### Applicability

- `operator_families`: <code>sparse_attention_nsa</code>
- `target_languages`: <code>triton</code>
- `gfx`: <code>gfx950</code>

#### Use when

- The kernel has a code path where the KV loop runs exactly one trip (all selected slots for a split fit one tile), e.g. small-batch sparse MLA decode
- That path splits the value head dimension into groups, each with its own KV gather, QK dot and PV dot accumulator
- Another path of the same kernel already uses full-width operands, which suggests the tile fits; confirm no scratch in the single-trip path's ISA after the change
- Recorded on fp8_e4m3 sparse MLA decode, Triton, gfx950

#### Try

- Load the full q tile once and gather each selected KV row once at full D_V width, keeping the rope tail as a separate small load
- Compute one full-width QK dot plus the tail dot, and one PV dot into a single full-width accumulator
- On a strictly single-trip path, drop the online-softmax alpha rescale, since the accumulator starts at zero
- Store the full-width accumulator directly in the epilogue and remove the now-dead per-group loads and accumulators
- Check the compiled ISA for VGPR count, scratch and barrier count before benchmarking, and re-run a same-slot control of the parent

#### Rationale

- Fewer, larger dots were associated with fewer layout conversions, LDS allocations and barriers in the engineer's ISA and TTGIR counts
- One contiguous full-width gather per KV row replaces several narrower strided gathers
- On a single trip, the rescale multiply on every accumulator is redundant work

#### Keep as alternatives

- Keep the per-group split when the full-width tile spills or lowers occupancy for the given D_V and BLOCK_H
- Apply full-width operands only on multi-trip paths and leave the single-trip path grouped
- Retune BLOCK_H or the split count instead of changing the contraction shape

<a id="fold-constant-dequant-scale-into-epilogue-normalization"></a>
### Should a constant dequant scale on the softmax P operand be applied per inner-loop dot or once in the epilogue normalization?

**Card:** `fold-constant-dequant-scale-into-epilogue-normalization` · **Type:** `performance_candidate` · **Evidence:** `reported_experience`

**Axes:** `compute_schedule`, `implementation_contract`

#### Applicability

- `operator_families`: <code>sparse_attention_nsa</code>
- `target_languages`: <code>triton</code>, <code>gluon</code>, <code>hip</code>, <code>flydsl</code>
- `gfx`: <code>gfx950</code>

#### Use when

- Online-softmax attention (dense or sparse selected-slot) whose P tile is quantized to a low-precision dot dtype with a single scale shared by all tiles and rows
- The accumulator update is linear in the dot result (acc = acc * alpha + dot(P, V) * scale), so a constant factor commutes with the alpha rescale
- The final normalization already multiplies acc by a reciprocal of the softmax denominator l

#### Try

- Drop the per-iteration multiply of each dot(P, V) result by the P dequant scale for every accumulator group
- Multiply the scale into the epilogue reciprocal (scale / l instead of 1 / l), keeping the l == 0 guard that yields zero output
- Check the runtime ISA for register count and scratch after the change, since the saving can be a few VGPRs rather than an occupancy step
- Measure seed and candidate alternately in the same GPU slot, because the expected gain is small

#### Rationale

- A constant factor can be pulled through the sum and through the alpha rescale of online softmax, so applying it once at the end is algebraically equivalent
- It removes one multiply per accumulator element per iteration; in the one recorded kernel the measured effect was 254 vs 256 VGPRs and a small timing gain

#### Keep as alternatives

- Keep the per-iteration scale multiply when the scale varies per tile, per block or per row of P
- If the quantization multiplier is already a power of two, moving the scale should be bit-identical; changing the multiplier alters fp8 rounding of P and needs its own correctness and accuracy check (untested)

<a id="one-trip-prologue-issue-gather-before-q-converts"></a>
### In a single-tile sparse-gather attention prologue, should the index-dependent KV gather be issued before the q dtype conversions?

**Card:** `one-trip-prologue-issue-gather-before-q-converts` · **Type:** `performance_candidate` · **Evidence:** `reported_experience`

**Axes:** `data_movement`, `compute_schedule`, `sparse_selection`

#### Applicability

- `operator_families`: <code>sparse_attention_nsa</code>
- `target_languages`: <code>triton</code>
- `gfx`: <code>gfx950</code>

#### Use when

- The path processes exactly one KV tile per split (all selected slots of the split fit one tile), so there is no loop to pipeline across
- The KV gather address depends on an index vector loaded in the same prologue
- The q loads and their dtype converts do not depend on the gather
- Memory waits on the target retire in issue order, so a convert placed after a later-issued load can wait on that load too

#### Try

- Issue the index load first, then the raw q loads without converting, then the index-dependent KV gather, and only then convert q
- Put the single-tile path in a constexpr branch selected by the launcher and write it as straight-line code that keeps the loop's tile math
- Keep the multi-trip pipelined path's order separate and A/B any reorder there on its own buckets
- Compare VGPR, AGPR, scratch and occupancy of the compiled kernel before and after the change

#### Rationale

- The engineer's account: q converts then wait only on the q loads, so they overlap the gather latency instead of sitting in front of it
- In the engineer's compile check, the straight-line one-trip branch also used fewer registers (244 VGPRs vs 280 including AGPRs) and occupancy rose from 1 to 2

#### Keep as alternatives

- Keep each q load fused with its convert, in the original order
- For multi-trip segments, use a manual register pipeline: issue the next tile's gather and the following tile's index load before the current tile's compute
- Compute QK and PV as full head-width dots on the single-tile path
