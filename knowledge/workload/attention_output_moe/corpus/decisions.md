## What must a post-attention monokernel return to the next layer?

`post-attention-preserve-handoff` · candidate only · fusion_boundary, numerical_contract, data_lifetime

### Use when

- The framework retains attention and passes its unprojected output plus the residual into a fused projection/MoE path.

### Actions

- Return reduced MoE output and the residual after attention as separate values.
- Leave the final MoE residual addition to the next input norm when using the PLAIN_ADD handoff.
- Preserve padded-row semantics: negative slots join no expert and produce zero MoE output; their seam residual is unspecified.

### Rationale

- The live caller records the returned buffers in the residual stream instead of immediately adding them.

### Alternatives

- Use the ordinary projection, residual/norm, router, expert and collective sequence.

## How should persistent fusion admission depend on compiled occupancy?

`post-attention-gate-compiled-residency` · candidate only · scheduling, dispatch, compilation

### Use when

- Progress depends on the whole persistent grid being resident.
- Resource use can vary by compiled shape or specialization.

### Actions

- Query occupancy for the compiled binary and block size, then reject a width if resident blocks per CU times CU count is smaller than the grid.
- Repeat the check after changing fusion extent, tile geometry or compiler version; keep an ordinary fallback outside the accepted envelope.

### Rationale

- FfnRunner.warm checks every compiled width against the 256-CTA grid before live execution.

### Alternatives

- Reduce resource pressure or redesign the scheduling/progress protocol.
- Use separate launches for stages that cannot meet the residency requirement.

## How can fused compute and collectives reuse peer buffers without accepting stale data?

`post-attention-peer-buffer-epochs` · candidate only · communication, synchronization, data_lifetime

### Use when

- Several layer/width runners share peer-visible storage with tagged payloads.

### Actions

- Share the epoch across every runner using the same peer buffer and keep the launch sequence consistent across ranks.
- Advance or recycle tags only after the required completion marks; preserve the tag-cycle clearing boundary and guards.

### Rationale

- The runner documents buffer-lifetime epoch ownership, and the kernel completes work before advancing the epoch and clearing a reused cycle.

### Alternatives

- Give independent runners independent storage and synchronization lifetimes.
- Keep ordinary collectives as the reference path.
