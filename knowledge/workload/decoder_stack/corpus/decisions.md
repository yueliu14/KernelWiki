## When can stages inside a persistent stack communicate through tagged mailboxes?

`stack-tagged-stage-mailboxes` · candidate only · scheduling, data_lifetime, synchronization

### Use when

- The target is the single-GPU static stage schedule with all required CTAs co-resident.
- Dependencies point to earlier stages and the payload/tag representation fits the chosen memory operations.

### Actions

- Publish payload and tag together, identify both the step and launch, and poll only the inputs needed by the consumer.
- Use the required memory scope/cache policy and preserve timeout/error handling.
- Account for mailbox storage and traffic as global scratch even though the stages share a launch.

### Rationale

- The kernel writes paired values and tags and polls them through device-scope buffer operations; it does not eliminate intermediate storage.

### Alternatives

- Separate the stages into launches with ordinary tensors.
- Use registers or LDS only where ownership and lifetime really allow it.

## Which state writes must survive fusion of a speculative verification stack?

`stack-preserve-verify-state` · candidate only · numerical_contract, data_lifetime, dispatch

### Use when

- The target runs four-token NEXTN target verification with per-request GDN/PLE scratch and QSA cache updates.

### Actions

- Keep per-token state/window snapshots in the request row consumed by accept/commit logic.
- Preserve KV/index-ring writes, residual outputs and padding rules; keep committed recurrent state distinct from speculative scratch.
- Use sequence positions for causal/context logic and MRoPE positions for rotary transforms where they differ.

### Rationale

- The fused stages must leave the same externally visible state for accept, draft and later target steps.

### Alternatives

- Keep the framework recurrent and attention paths for unsupported verification contracts.

## How should cross-layer fusion depth be bounded?

`stack-bound-fusion-depth` · candidate only · fusion_boundary, compilation, measurement

### Use when

- Layer bodies are unrolled at compile time and each supported row shape requires specialization.

### Actions

- Choose a bounded layer group and preserve special first/prelude and final-mixer boundaries.
- Compare compilation cost, code size, resource use and steady-state latency while retaining identical state semantics.
- Count the 13 stack launches separately from logits, host-issued epoch updates and other serving work.

### Rationale

- The reviewed plan uses layer 0, layers 1..3, then groups of four; the documentation gives code size and compilation time as reasons for the bound.

### Alternatives

- Use one layer per launch.
- Evaluate larger groups only with a measured resource and compilation budget.
